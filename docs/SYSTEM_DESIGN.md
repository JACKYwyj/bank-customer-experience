## 1. 项目背景与目标

### 1.1 项目背景

银行网点的智能化建设不仅要提高业务效率，也要解决客户在等待、操作受阻和异常处理过程中困难无法及时发现、帮助难以及时到达、问题难以连续交接的服务痛点。

**核心问题：**
- 无解释的等待
- 反复失败和重复叙述
- 服务介入通常已经滞后

这些会积累客户不满，增加投诉升级和信任流失风险。

### 1.2 项目目标

本项目旨在构建一个完整的智慧银行网点客户体验提升系统，核心目标是：

- **效率提升**：通过AI自动化处理标准化业务，释放人工资源
- **体验优化**：多模态情绪感知实现个性化、情感化的服务
- **隐私合规**：emoAIsec隐私安全框架确保数据合规
- **及时响应**：把可能演变为投诉和信任流失的服务问题处理在办理过程中

### 1.3 项目定位

项目定位为现有网点服务体系的**辅助工具**，不替代柜员判断和现场服务。系统重点解决三类问题：

1. 客户在等待和操作受阻时需求难以及时发现
2. 工作人员接手时缺少前序信息
3. 处理结果未能沉淀为持续改进依据

## 4. 核心模块设计

### 4.1 多模态情绪识别模块

#### 4.1.1 功能描述

融合面部表情、语音语调、文本语义三个维度的情绪识别，为网点服务提供实时情绪感知能力。

#### 4.1.2 技术架构

```
┌─────────────────────────────────────────────────────────────┐
│                    多模态情绪融合层                          │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐  │
│  │ 面部情绪    │  │ 语音情绪    │  │ 文本情绪            │  │
│  │ 分析模块    │  │ 分析模块    │  │ 分析模块            │  │
│  │ (权重0.40) │  │ (权重0.35) │  │ (权重0.25)         │  │
│  └──────┬──────┘  └──────┬──────┘  └──────────┬─────────┘  │
│         │                │                     │            │
│         ▼                ▼                     ▼            │
│  ┌─────────────────────────────────────────────────────┐    │
│  │              CrossModalFusion 融合引擎                │    │
│  │         - 仅纳入置信度 > 0.5 的有效模态               │    │
│  │         - 缺失模态时按有效权重重新归一化              │    │
│  └──────────────────────────┬──────────────────────────┘    │
│                             │                                │
│                             ▼                                │
│  ┌─────────────────────────────────────────────────────┐    │
│  │              情绪融合输出                            │    │
│  │     焦虑(anxiety) │ 愤怒(anger) │ 受挫(frustration) │    │
│  └─────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

#### 4.1.3 融合权重设计（原型初始参数）

| 模态 | 默认权重 | 有效阈值 | 说明 |
|------|----------|----------|------|
| 面部表情 | 0.40 | 置信度 > 0.5 | 缺失时按0.60/0.35归一化 |
| 语音语调 | 0.35 | 置信度 > 0.5 | 缺失时按0.40/0.65归一化 |
| 文本语义 | 0.25 | 置信度 > 0.5 | 缺失时按0.40/0.60归一化 |

> **重要**：以上权重为基于研究论文设计的原型初始参数，实际网点验证前需通过人工标注、误报与漏报、响应时长、问题解决率和一线人员反馈进行校准。

#### 4.1.4 预设输出（原型阶段）

| 输入类型 | 预设情绪 | 置信度 |
|----------|----------|--------|
| 面部输入 | 焦虑 | 0.85 |
| 语音输入 | 焦虑 | 0.78 |
| 文本输入 | 基于关键词计数 | - |

#### 4.1.5 告警规则

| 情绪标签 | 触发条件 | 建议响应 |
|----------|----------|----------|
| **焦虑 (anxiety)** | 分值 ≥ 0.5 且持续 ≥ 60秒 | 先解释进度并观察；中等信号持续出现时避免过度干预 |
| **愤怒 (anger)** | 分值 ≥ 0.8 且持续 ≥ 30秒 | 建议人工接手或主管协调；高风险信号应快速响应 |
| **受挫 (frustration)** | 分值 ≥ 0.6 且持续 ≥ 90秒 | 建议服务修复与人工协助；持续受阻后再介入 |
| **未达条件** | 不满足上述条件 | 继续当前流程并保留人工求助入口 |

> **注意**：识别置信度不等于经过验证的心理强度，应作为业务参考分值，待校准后使用。

### 4.2 共情交互模块

#### 4.2.1 功能描述

基于上下文和模板生成共情回应及服务修复话术，减少客户重复叙述，提供明确回应并恢复对服务过程的信任。

#### 4.2.2 技术流程

```
客户输入 → 情绪信息整合 → 上下文理解 → 话术模板匹配 → 共情回应生成
                                              ↓
                                      必要时触发服务修复
```

#### 4.3.2 核心规则

| 情绪标签 | 触发条件 | 建议响应 |

| anger | 参考分值≥0.8 且持续≥30秒 | 建议人工接手或主管协调 |
| frustration | 参考分值≥0.6 且持续≥90秒 | 建议服务修复与人工协助 |

### 4.5 空间优化模块

#### 4.5.1 功能描述

基于Z-AHP与Z-TOPSIS评价体系，为网点空间调整提供辅助判断。

#### 4.5.2 评价指标

| 指标类型 | 指标名称 | 优化方向 |
|----------|----------|----------|
| 等待数据 | 平均等待时间 | 越低越好 |
| | 平均服务时间 | 越低越好 |
| 业务数据 | 业务成功率 | 越高越好 |
| | 满意度评分 | 越高越好 |
| | 情绪积极率 | 越高越好 |
| | 投诉率 | 越低越好 |
| 空间数据 | 面积效率 | 越高越好 |
| | 功能布局评分 | 越高越好 |
| | 动线评分 | 越高越好 |

#### 4.5.3 评价方法

采用 **Z-AHP** 与 **Z-TOPSIS** 评价方法：

1. **数据标准化**：统一指标方向和量纲
2. **权重计算**：通过AHP层次分析法计算指标权重
3. **TOPSIS评价**：计算与理想解的相对贴近度
4. **输出优化建议**：基于评价结果生成网点优化建议

### 4.6 隐私保护模块

#### 4.6.1 功能描述

确保客户数据隐私安全，支持联邦学习架构。

#### 4.6.2 技术方案

- **联邦学习**：各网点数据本地训练，仅上传权重文件
- **差分隐私**：保护个体数据不被反向推断
- **端侧加密**：敏感数据在传输和存储时加密

## 5. 应用场景设计

### 5.1 等候场景中的进度解释与分流

**场景描述**：客户长时间等待却不知道进度

**系统动作**：
1. 客户反复询问进度或持续表现焦虑时，系统先一步完成识别
2. 提醒大堂人员核实原因
3. 说明预计办理顺序
4. 检查是否存在资料缺失或业务分流可能

### 5.2 自助操作场景中的分步引导

**场景描述**：客户在智能柜员机上反复失败却无人响应

**系统动作**：
1. 依据操作日志识别重复返回、同一步骤多次失败和主动求助
2. 结合客户表达决定是否提示
3. 对于一般困难，界面先提供简短步骤说明和清晰的人工帮助入口
4. 客户仍无法完成时，系统总结当前步骤与已完成事项并提交给大堂人员

### 5.3 复杂业务咨询与异常服务修复

**场景描述**：账户异常和资金问题处理中多次叙述同一情况

**系统动作**：
1. 先核实事实、明确可处理事项和办理时限
2. 给出适度的理解与解释
3. 涉及争议或紧急资金需求时，直接转交具备相应权限的人员处理

## 7. 效益评估方法

### 7.1 评估指标

| 类别 | 指标 |
|------|------|
| **服务效率** | 首次响应时长、重复询问次数 |
| **业务完成** | 自助办理完成率、问题解决率 |
| **客户体验** | 客户满意度、持续使用意愿 |
| **运营成本** | 投诉升级率、人工工作量、系统误报率、漏报率 |

### 7.2 评估方法

采用**试点-对照**设计：
- "试点网点试运行前后变化减去对照网点同期变化"
- 报告区间估计
- 满意度变化以分值或百分点分别表述，不混用相对增幅

> **重要**：情绪识别输出只用于辅助过程分析；客户是否满意、投诉是否解决，应以客户反馈和业务结果为准。

## 8. 实施计划

### 第一阶段
- 统一会话、流程和业务事项标识
- 接入排队与操作日志

### 第二阶段
- 连接识别、话术和流程接口
- 将建议转换为人员待办
- 设置超时升级路径

### 第三阶段
- 接入真实模型
- 完成离线评估后开展有限现场试用

### 第四阶段
- 将服务状态、处理结果和客户评价持久化回写
- 形成业务闭环

## 9. 核心技术约束

### 9.1 当前实现边界

- 会话和流程状态主要保存在服务内存中
- 接入时需补充数据持久化、异常重试、运行监测和消息处理
- 文本分析主要采用关键词规则

### 9.2 待完成项

- 真实模型接入
- 跨服务编排
- 数据持久化
- 银行业务系统联调
